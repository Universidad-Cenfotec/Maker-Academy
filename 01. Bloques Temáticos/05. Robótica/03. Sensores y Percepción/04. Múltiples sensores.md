## Descripción

Un robot con un solo sensor tiene un comportamiento limitado. Los robots más interesantes —y el SumoBot en particular— combinan varios sensores a la vez, cada uno aportando un tipo de información distinto. El reto deja de ser "leer un sensor" y pasa a ser "decidir qué sensor manda cuando hay información contradictoria".

**Si múltiples sensores fueran los sentidos de una persona cruzando la calle: los ojos ven el semáforo, los oídos escuchan un carro acercándose. Si el semáforo está en verde pero el oído detecta peligro inminente, la persona no cruza. El oído "gana" en ese momento porque la seguridad tiene prioridad sobre la señal visual. Un robot bien programado necesita ese mismo criterio de prioridad.**

## Propósito

Que el docente comprenda por qué combinar sensores requiere una lógica de prioridad explícita, sepa identificar qué sensor debe "mandar" en caso de conflicto, y pueda guiar a los estudiantes en la programación de un robot con sensores de línea y distancia combinados, como en el caso del SumoBot.

---

## Por qué combinar sensores

Cada sensor percibe un solo tipo de información del entorno. Un robot que solo tiene sensor de distancia puede encontrar al adversario, pero no sabe si está a punto de salirse de la zona de competencia. Un robot que solo tiene sensores de línea puede evitar el borde, pero no puede buscar activamente al rival. Combinar ambos sensores le da al robot una percepción más completa, parecida a cómo una persona usa varios sentidos a la vez para tomar una sola decisión.

---

## El problema de la prioridad

Cuando un robot tiene varios sensores activos al mismo tiempo, puede ocurrir que dos sensores "pidan" comportamientos distintos en el mismo instante. Por ejemplo: el sensor de distancia detecta al adversario y quiere avanzar a máxima velocidad, pero al mismo tiempo el sensor de línea detecta el borde del dohyo y "pide" retroceder.

**Si el programa no define qué sensor manda, el robot puede intentar hacer ambas cosas a la vez, o alternar entre ellas de forma errática (parpadeando entre avanzar y retroceder).** La solución es establecer una jerarquía clara de prioridad antes de escribir el código, no durante.

---

## Tabla de prioridades para SumoBot

| Prioridad | Sensor | Condición | Acción | Justificación |
|---|---|---|---|---|
| 1 (máxima) | Sensores de línea | Detecta el borde del dohyo | Retroceder y girar, alejándose del borde | Salirse del dohyo significa perder el combate de inmediato; es la condición más urgente |
| 2 | Sensor de distancia | Detecta al adversario (y no hay alerta de borde) | Avanzar a máxima velocidad hacia el objetivo | Es el objetivo del combate, pero solo si no hay riesgo de salirse |
| 3 (mínima) | Ninguno activo | No detecta línea ni adversario | Girar en el lugar buscando al rival | Comportamiento por defecto cuando no hay información relevante |

**Regla general:** los sensores relacionados con la seguridad o la permanencia dentro de los límites de competencia siempre tienen la prioridad más alta, por encima de los sensores relacionados con el objetivo del reto.

## Código: combinación de sensor de línea y sensor de distancia

```cpp
// Sensores de línea (detectan el borde del dohyo)
const int pinLineaIzq = A0;
const int pinLineaDer = A1;
const int umbralLinea = 500;

// Sensor de distancia (detecta al adversario)
const int pinTrig = 9;
const int pinEcho = 10;
const int umbralAdversario = 30; // cm

long medirDistancia() {
  digitalWrite(pinTrig, LOW);
  delayMicroseconds(2);
  digitalWrite(pinTrig, HIGH);
  delayMicroseconds(10);
  digitalWrite(pinTrig, LOW);
  long duracion = pulseIn(pinEcho, HIGH);
  return duracion / 58;
}

void setup() {
  pinMode(pinTrig, OUTPUT);
  pinMode(pinEcho, INPUT);
}

void loop() {
  int lineaIzq = analogRead(pinLineaIzq);
  int lineaDer = analogRead(pinLineaDer);
  long distancia = medirDistancia();

  bool bordeIzq = lineaIzq > umbralLinea;
  bool bordeDer = lineaDer > umbralLinea;

  // PRIORIDAD 1: el borde del dohyo manda sobre cualquier otra cosa
  if (bordeIzq || bordeDer) {
    detener();
    delay(100);
    retroceder();
    delay(300);
    if (bordeIzq) {
      pivoteDerecha(150); // se detectó el borde a la izquierda: girar a la derecha
    } else {
      pivoteIzquierda(150); // se detectó el borde a la derecha: girar a la izquierda
    }
    delay(300);
    return; // no evaluar el sensor de distancia en este ciclo
  }

  // PRIORIDAD 2: si no hay riesgo de borde, buscar al adversario
  if (distancia < umbralAdversario && distancia > 0) {
    avanzar(); // modo ataque
  } else {
    // PRIORIDAD 3: comportamiento por defecto
    pivoteDerecha(120); // modo búsqueda
  }
}
```

**Punto clave del código:** la instrucción `return` dentro del bloque de prioridad 1 asegura que, si se detectó el borde, el programa no continúe evaluando el sensor de distancia en ese mismo ciclo. Esto evita que ambos comportamientos compitan entre sí.

## Más allá de dos sensores

La misma lógica de prioridad se puede extender a robots con tres o más sensores (por ejemplo, dos de línea, un sensor de distancia y un sensor de luz). El principio no cambia: antes de programar, se define una tabla de prioridades como la de este documento, y el código se estructura de arriba hacia abajo, revisando primero la condición de mayor prioridad.

| Cantidad de sensores | Complejidad de la lógica | Recomendación |
|---|---|---|
| 1 sensor | Baja: una condición, una acción | Adecuado para primeras sesiones |
| 2 sensores | Media: requiere definir prioridad | SumoBot básico, evasión con orientación |
| 3 o más sensores | Alta: requiere tabla de prioridad escrita antes de programar | Proyectos avanzados o de competencia |

## Nota docente

Antes de dejar que el grupo programe, vale la pena hacer el ejercicio de la tabla de prioridades en papel, sin código: preguntar "¿qué debe pasar si los dos sensores detectan algo importante al mismo tiempo?" y dejar que el grupo discuta y decida antes de tocar el teclado. Los equipos que se saltan este paso casi siempre terminan con un robot que se comporta de forma errática, porque programan reacciones aisladas sin haber decidido de antemano cuál gana en caso de conflicto.
