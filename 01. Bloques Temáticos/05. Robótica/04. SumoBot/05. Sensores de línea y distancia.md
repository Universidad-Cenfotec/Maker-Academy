## Descripción

El SumoBot no usa un solo sensor: combina el sensor de línea y el sensor de distancia en una misma lógica de decisión. Este archivo explica cómo se articulan ambos sensores dentro del programa de un SumoBot, con la prioridad que define el comportamiento del robot en competencia.

**Si el robot fuera un boxeador con los ojos vendados que además siente el piso bajo sus pies: primero necesita saber si está a punto de salirse del ring (lo siente con los pies) antes de decidir hacia dónde lanzar el golpe (lo intenta detectar con las manos extendidas). Sentir el borde siempre tiene prioridad sobre atacar.**

## Por qué se necesita una prioridad clara

Un SumoBot recibe información de dos sensores al mismo tiempo, pero solo puede ejecutar una acción en cada instante del programa. Si el programa no define con claridad qué sensor manda primero, el robot puede terminar avanzando hacia el rival justo cuando está a punto de salirse del dohyo, perdiendo la ronda por su propio movimiento.

**Regla de prioridad en SumoBot:**

1. **Primero, evitar salirse del dohyo.** Si el sensor de línea detecta el borde, esa señal siempre gana, sin importar lo que indique el sensor de distancia.
2. **Solo si no hay riesgo de borde, atacar si se detecta al rival.** El sensor de distancia decide entre "modo búsqueda" (girar) y "modo ataque" (avanzar).

Esta jerarquía refleja una lógica sencilla: no sirve de nada atacar al rival si el resultado es salirse uno mismo del área de competencia.

---

## Lógica combinada en pseudocódigo

```
si (sensor de línea detecta borde):
    retroceder y girar (alejarse del borde)
si no, si (sensor de distancia detecta al rival):
    avanzar (modo ataque)
si no:
    girar en el lugar (modo búsqueda)
```

## Ejemplo de código Arduino con la lógica combinada

```cpp
const int pinSensorIzq   = A0;
const int pinSensorDer   = A1;
const int umbralBorde    = 700;   // valor calibrado sobre el dohyo real
const int pinTrig        = 9;
const int pinEcho        = 10;
const int umbralRival    = 30;    // cm

long medirDistancia() {
  digitalWrite(pinTrig, LOW);
  delayMicroseconds(2);
  digitalWrite(pinTrig, HIGH);
  delayMicroseconds(10);
  digitalWrite(pinTrig, LOW);
  long duracion = pulseIn(pinEcho, HIGH);
  return duracion / 58;
}

void retroceder() {
  analogWrite(ENA, 150); analogWrite(ENB, 150);
  digitalWrite(IN1, LOW);  digitalWrite(IN2, HIGH);
  digitalWrite(IN3, LOW);  digitalWrite(IN4, HIGH);
}

void avanzar() {
  analogWrite(ENA, 200); analogWrite(ENB, 200);
  digitalWrite(IN1, HIGH); digitalWrite(IN2, LOW);
  digitalWrite(IN3, HIGH); digitalWrite(IN4, LOW);
}

void girarBuscando() {
  analogWrite(ENA, 150); analogWrite(ENB, 150);
  digitalWrite(IN1, HIGH); digitalWrite(IN2, LOW);
  digitalWrite(IN3, LOW);  digitalWrite(IN4, HIGH);
}

void setup() {
  pinMode(pinTrig, OUTPUT);
  pinMode(pinEcho, INPUT);
}

void loop() {
  int lecturaIzq = analogRead(pinSensorIzq);
  int lecturaDer = analogRead(pinSensorDer);
  bool veoBorde = (lecturaIzq > umbralBorde) || (lecturaDer > umbralBorde);

  if (veoBorde) {
    // Prioridad 1: alejarse del borde, sin importar el rival
    retroceder();
    delay(300);
  } else {
    long distancia = medirDistancia();
    if (distancia < umbralRival && distancia > 0) {
      avanzar(); // Prioridad 2: atacar al rival detectado
    } else {
      girarBuscando(); // Sin borde ni rival detectado: buscar
    }
  }
}
```

**Nota importante:** el bloque de `veoBorde` se evalúa siempre primero en el `loop()`. Esto garantiza que ninguna condición de ataque pueda "ganarle" a la condición de seguridad del borde.

## Errores comunes al combinar ambos sensores

- Invertir la prioridad y revisar primero el sensor de distancia: el robot puede avanzar hacia el rival mientras ya está sobre el borde.
- Usar el mismo umbral de línea calibrado en un piso genérico en lugar del dohyo real, lo que genera falsas alarmas o detecciones tardías.
- No incluir un tiempo de retroceso suficiente al detectar el borde, lo que hace que el robot vuelva a tocarlo de inmediato.

## Nota docente

Conviene pedirle al grupo que explique en voz alta, antes de programar, cuál sensor debe "ganar" en caso de conflicto y por qué. Esta discusión previa evita que la prioridad se decida de forma accidental por el orden en que se escribieron las líneas de código, y refuerza la idea de que programar una prioridad es una decisión de diseño, no un detalle técnico menor.
