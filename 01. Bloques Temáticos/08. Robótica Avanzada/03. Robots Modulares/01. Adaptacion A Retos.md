## Descripción

Un robot que solo sirve para una tarea obliga a rehacerlo cada vez que cambia el reto. Este tema plantea lo contrario: el CenfoBot como una plataforma que se adapta. Adaptar no es reconstruir; es decidir qué parte del robot ya resuelve el problema nuevo y qué parte hay que cambiar. Esa decisión —qué se conserva, qué se agrega y qué se quita— es el primer paso de cualquier rediseño, y hacerla bien ahorra tiempo, materiales y errores.

**Si el robot es un carro de carreras, cambiar de pista no significa construir otro carro: significa cambiar las llantas, ajustar la suspensión y dejar el motor donde está.**

---

## Propósito

Explicar qué significa adaptar un robot a un reto nuevo, cómo identificar las partes que se conservan y las que cambian, y por qué la adaptación por partes es más eficiente que la reconstrucción completa.

---

## Contenido

### El problema de empezar de cero

Cuando cambia el reto, la reacción natural es desarmar el robot y armarlo otra vez. Funciona, pero tiene un costo que no siempre se ve: se pierde todo lo que ya se había ajustado y probado. La calibración de los sensores, las constantes del controlador, la posición de las ruedas, el cableado que ya no se enredaba: todo eso se va con el robot viejo.

Adaptar es la alternativa. Se parte de lo que ya funciona y se cambia solo lo necesario. El robot no vuelve a cero; avanza desde donde estaba.

La diferencia no es solo de tiempo. Un robot reconstruido tiene que volver a demostrar que funciona; un robot adaptado conserva la confianza en las partes que no se tocaron.

---

### Qué se conserva, qué se agrega, qué se quita

Adaptar un robot es tomar tres decisiones sobre cada pieza.

**Conservar.** La pieza sigue siendo útil para el reto nuevo, tal como está. El chasis, los motores y la placa suelen conservarse en casi cualquier reto: son la base de movimiento y control.

**Agregar.** El reto nuevo exige algo que el robot no tiene. Un sensor ultrasónico para evasión, un arreglo de infrarrojos para seguir línea, un servo para levantar un objeto.

**Quitar.** La pieza estorba, pesa, consume energía o interfiere con lo nuevo. Un arreglo de cinco sensores de línea no ayuda en una prueba de sumo, y el cableado adicional solo estorba.

La decisión de quitar es la que más se resiste, porque parece un desperdicio. Pero una pieza que no se usa sigue pesando, sigue consumiendo y sigue siendo un punto de falla.

---

### El mismo CenfoBot, tres retos

Un ejemplo concreto ayuda a ver el patrón. El mismo chasis con IdeaBoard enfrenta tres retos distintos.

**Seguir una línea.** Se conservan chasis, motores y placa. Se agrega un arreglo de sensores infrarrojos apuntando al piso. Se quita cualquier sensor frontal que no aporte. El programa es el controlador PID.

**Evadir obstáculos.** Se conservan chasis, motores y placa. Se agrega un sensor ultrasónico al frente y, si el reto lo pide, sensores laterales. Se quitan los infrarrojos de piso. El programa es la tabla de prioridades.

**Sumo.** Se conservan chasis, motores y placa. Se agregan sensores de borde para no salir del dojo y un sensor frontal para detectar al oponente. Se quitan los sensores de piso que no sean de borde. El programa combina búsqueda y empuje.

En los tres casos, más de la mitad del robot es la misma. Lo que cambia es una parte pequeña, y esa parte pequeña es la que define el reto.

---

### La adaptación también es de software

Cambiar piezas físicas es solo la mitad. Cada configuración nueva necesita un programa que sepa qué tiene.

Un robot adaptado con un sensor ultrasónico nuevo necesita código que lo lea, lo interprete y actúe en consecuencia. Ese código no reemplaza al anterior: se suma. El control de motores, la lectura de la placa y el ciclo principal siguen siendo los mismos.

Aquí se ve por qué importa la modularidad de software del tema siguiente: si el programa está separado en piezas —sensores, decisión, movimiento—, adaptarlo es cambiar una pieza. Si está escrito de corrido, adaptarlo es reescribirlo.

### Ejemplo en CircuitPython

El código siguiente muestra una adaptación concreta: el mismo programa base, con un módulo de comportamiento que se elige según el reto.

```python
# Adaptación a retos - CenfoBot / IdeaBoard
import board
from ideaboard import IdeaBoard
from time import sleep

ib = IdeaBoard()

# --- Configuración del reto ---
# "linea", "obstaculos" o "sumo"
RETO = "linea"

# --- Módulos de hardware disponibles ---
ir_izq = ib.AnalogIn(board.IO36)
ir_der = ib.AnalogIn(board.IO32)
UMBRAL_IR = 2950

# El ultrasónico solo se usa si el reto lo requiere
if RETO in ("obstaculos", "sumo"):
    from ideaboard import Ultrasonic
    distancia = Ultrasonic(ib, board.IO25, board.IO26)


def seguir_linea():
    izq = ir_izq.value < UMBRAL_IR
    der = ir_der.value < UMBRAL_IR
    if izq and not der:
        ib.motor_1.throttle = 0.2
        ib.motor_2.throttle = 0.6
    elif der and not izq:
        ib.motor_1.throttle = 0.6
        ib.motor_2.throttle = 0.2
    else:
        ib.motor_1.throttle = 0.5
        ib.motor_2.throttle = 0.5


def evadir_obstaculos():
    d = distancia.distance
    if d < 15:
        ib.motor_1.throttle = -0.5
        ib.motor_2.throttle = 0.5
        sleep(0.3)
    else:
        ib.motor_1.throttle = 0.6
        ib.motor_2.throttle = 0.6


def sumo():
    d = distancia.distance
    if d < 30:
        ib.motor_1.throttle = 1.0
        ib.motor_2.throttle = 1.0
    else:
        ib.motor_1.throttle = 0.4
        ib.motor_2.throttle = -0.4


COMPORTAMIENTOS = {
    "linea": seguir_linea,
    "obstaculos": evadir_obstaculos,
    "sumo": sumo,
}

comportamiento = COMPORTAMIENTOS[RETO]

while True:
    comportamiento()
    sleep(0.01)
```

Lo que se conserva es el ciclo principal y el acceso a los motores. Lo que se cambia es una sola función, elegida al inicio. Adaptar el robot a otro reto es cambiar una línea y conectar los sensores que ese reto necesita.

### El mismo enfoque en C++ (Arduino)

```cpp
// Adaptación a retos - CenfoBot / IdeaBoard (Arduino)
#include <IdeaBoard.h>
#include <Ultrasonic.h>

IdeaBoard ib;
Ultrasonic sonar(25, 26);

enum Reto { LINEA, OBSTACULOS, SUMO };
const Reto RETO = LINEA;

const int UMBRAL_IR = 2950;

void seguirLinea() {
  bool izq = analogRead(36) < UMBRAL_IR;
  bool der = analogRead(32) < UMBRAL_IR;
  if (izq && !der) {
    ib.motor1.throttle(0.2);
    ib.motor2.throttle(0.6);
  } else if (der && !izq) {
    ib.motor1.throttle(0.6);
    ib.motor2.throttle(0.2);
  } else {
    ib.motor1.throttle(0.5);
    ib.motor2.throttle(0.5);
  }
}

void evadirObstaculos() {
  long d = sonar.read();
  if (d < 15) {
    ib.motor1.throttle(-0.5);
    ib.motor2.throttle(0.5);
    delay(300);
  } else {
    ib.motor1.throttle(0.6);
    ib.motor2.throttle(0.6);
  }
}

void sumo() {
  long d = sonar.read();
  if (d < 30) {
    ib.motor1.throttle(1.0);
    ib.motor2.throttle(1.0);
  } else {
    ib.motor1.throttle(0.4);
    ib.motor2.throttle(-0.4);
  }
}

void setup() {
  ib.begin();
  Serial.begin(115200);
}

void loop() {
  switch (RETO) {
    case LINEA:      seguirLinea(); break;
    case OBSTACULOS: evadirObstaculos(); break;
    case SUMO:       sumo(); break;
  }
  delay(10);
}
```

La estructura es la misma: un comportamiento por reto y un selector que decide cuál corre.

### La misma idea con bloques (IdeaScratch)

En IdeaScratch la adaptación se arma con **bloques personalizados**, uno por comportamiento, y un bloque principal que llama al que corresponde.

- Un bloque personalizado **"seguir línea"** con la lógica de dos sensores.
- Un bloque personalizado **"evadir obstáculo"** con la lectura del ultrasónico.
- Un bloque personalizado **"modo sumo"** con la detección y el empuje.
- Un bloque principal con un "si [reto] = [línea] entonces" que elige cuál ejecutar dentro del ciclo permanente.

### Adaptar bien es decidir rápido

La adaptación tiene un valor práctico que va más allá del aula: en una competencia, el robot que se reconfigura entre rondas tiene más oportunidades que el que hay que reconstruir.

Eso exige que la decisión de qué cambiar sea rápida y segura. Un equipo que sabe de memoria qué piezas son su base y cuáles son específicas del reto puede reconfigurar en minutos. Uno que no lo sabe empieza a desarmar y descubre a mitad de camino que necesitaba conservar algo.

La regla práctica es simple: **identificar la base del robot y tratarla como intocable**. Todo lo demás es intercambiable.

---

### Por qué esto importa para lo que viene

La adaptación es la aplicación práctica de la modularidad. Antes de diseñar módulos que se acoplan —el tema siguiente— hay que entender qué partes del robot merecen ser módulos y cuáles son la base fija.

Y después de adaptar, siempre queda la pregunta de si el robot sigue siendo estable con las piezas nuevas. Esa es la materia del tercer tema de este módulo.

## Notas docentes

La adaptación se entiende como decisión, no como construcción. Conviene presentar un reto nuevo y pedir que se identifiquen las piezas que se conservan antes de tocar el robot. Esa lista es el verdadero ejercicio.

La tentación de reconstruir es fuerte y vale la pena nombrarla. Reconstruir parece más limpio, pero borra la calibración y las pruebas acumuladas. Mostrar cuánto tiempo se pierde en recalibrar hace evidente el costo.

El concepto de base intocable es el que conviene fijar. Chasis, motores y placa son la base; sensores y accesorios son lo intercambiable. Con esa distinción, la adaptación se vuelve una decisión rápida y no una reconstrucción disfrazada.

El ejemplo de código se lee por su estructura de selección, no por la lógica de cada comportamiento, que ya se trabajó en los módulos anteriores.

Este tema es solo teoría. La reconfiguración real del CenfoBot entre retos y la medición de tiempos de adaptación se dejan para las mini-lecciones y las prácticas guiadas.
