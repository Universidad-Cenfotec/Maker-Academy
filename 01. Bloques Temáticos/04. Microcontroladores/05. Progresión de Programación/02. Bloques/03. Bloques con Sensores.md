## Descripción

Un programa que no interactúa con el mundo físico es, en esencia, un cálculo. Un programa que lee sensores y reacciona a ellos en tiempo real es un **sistema reactivo**: cambia su comportamiento según el estado del entorno. Este salto conceptual es uno de los más importantes del bloque de microcontroladores.

Esta guía describe cómo conectar sensores en entornos de bloques y cómo construir programas que tomen decisiones basadas en los valores del mundo real.

---

## El flujo de trabajo con sensores en bloques

```
1. Conectar el sensor al pin correcto de la placa
2. Leer el valor del sensor en el monitor serial / visor de datos
3. Anotar el rango real (valor mínimo y máximo en las condiciones del proyecto)
4. Definir el umbral de decisión
5. Escribir la lógica condicional basada en ese umbral
6. Probar y ajustar el umbral si el comportamiento no es el esperado
```

El paso 2 es el más frecuentemente omitido y el que más frustraciones genera. No se puede diseñar un umbral correcto sin saber qué valores produce el sensor real.

## Ejemplo 1: Luz que se enciende en la oscuridad (micro:bit + MakeCode)

**Hardware:** micro:bit V2 (tiene sensor de luz integrado en los LEDs)

**En MakeCode:**
```
para siempre
    si [nivel de luz] < [100] entonces
        mostrar ícono [corazón]
    si no
        borrar pantalla
```

**Calibración:**
1. Abrir la consola serial de MakeCode.
2. Agregar temporalmente un bloque "serial escribir valor 'luz' = [nivel de luz]".
3. Observar los valores con luz de ambiente y con la mano cubriendo los LEDs.
4. Ajustar el umbral (100 en el ejemplo) según los valores reales observados.

## Ejemplo 2: Ventilador de temperatura (Arduino + Scratch/Snap4Arduino)

**Hardware:** Arduino UNO + sensor NTC (termistor) en A0 + motor DC con driver

**Lógica:**
```
para siempre
    lectura = leer pin analógico A0
    temperatura = mapear(lectura, 0, 1023, 0, 100)  // calibrar según el sensor
    
    si temperatura > 30 entonces
        encender motor (pin 9 HIGH)
    si no
        apagar motor (pin 9 LOW)
```

## El concepto de umbral

El umbral es la línea de decisión: el valor a partir del cual el sistema cambia de comportamiento. Definir el umbral es una decisión de diseño, no un hecho técnico. El mismo sensor en distintos ambientes requiere umbrales distintos.

**Preguntas para definir el umbral:**
- ¿Cuál es el valor cuando la condición que me interesa definitivamente existe?
- ¿Cuál es el valor cuando la condición definitivamente no existe?
- ¿Hay variación o ruido en el sensor que pueda causar que el umbral se cruce por error?

---

## Histéresis: evitar el parpadeo en el umbral

Cuando el valor del sensor oscila alrededor del umbral (por ruido o condiciones cambiantes), el sistema puede activarse y desactivarse rápidamente de forma incontrolada. La solución es usar **histéresis**: dos umbrales en lugar de uno.

```
si [valor] > [umbral_alto] entonces → activar
si [valor] < [umbral_bajo] entonces → desactivar
(si el valor está entre los dos umbrales, mantener el estado anterior)
```

Por ejemplo, para un ventilador que se activa a 30°C y se desactiva a 27°C (no a exactamente 30°C), lo que evita que esté encendiéndose y apagándose constantemente cuando la temperatura ronda los 30°C.

En bloques:

```
para siempre
    lectura = leer sensor
    
    si [ventilador apagado] y [lectura > 700] entonces
        encender ventilador
        establecer [estado] en "encendido"
    
    si [ventilador encendido] y [lectura < 500] entonces
        apagar ventilador
        establecer [estado] en "apagado"
```

## Proyectos de nivel medio con sensores y bloques

| Proyecto | Sensores | Actuadores | Concepto clave |
|---|---|---|---|
| Riego automático | Sensor de humedad de suelo | Bomba de agua o LED indicador | Umbral, sistema reactivo |
| Semáforo de ruido | Micrófono | LEDs de 3 colores | Rangos múltiples |
| Luz que sigue el día | LDR (sensor de luz) | LED de brillo variable (PWM) | Sensor analógico, mapeo |
| Alarma de movimiento | PIR (sensor infrarrojo pasivo) | Buzzer | Señal digital de sensor |

## Notas docentes

La sesión de "conocer el sensor" antes de programar la lógica es una de las más valiosas del bloque. Dedicar los primeros 15 minutos de la sesión solo a observar los valores del sensor en distintas condiciones (antes de escribir ninguna lógica condicional) cambia completamente la calidad del trabajo posterior.

Un error frecuente: los estudiantes asumen que el sensor produce valores en un rango estandarizado. En realidad, el rango depende del circuito, la plataforma, la iluminación del aula y muchos factores más. El modelo correcto es: "primero mido, luego programo".
