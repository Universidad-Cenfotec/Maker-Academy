## Propósito

Evaluar la programación física es diferente a evaluar programación en pantalla. El resultado de un proyecto de microcontroladores tiene una dimensión física (el circuito, los componentes, la pieza que se mueve o la luz que se enciende) y una dimensión lógica (el código que controla ese comportamiento). Ambas deben estar presentes para que la evaluación sea justa y completa.

Los dos instrumentos de esta carpeta están diseñados para capturar esas dos dimensiones: el proceso (la lista de cotejo) y la calidad del resultado (la rúbrica).

## Relación entre los instrumentos

La lista de cotejo captura el proceso: ¿el estudiante verificó las conexiones antes de encender? ¿Probó por partes antes de conectar todo? ¿Usó el monitor serial para depurar? Muchos de esos comportamientos son invisibles en el resultado final pero son exactamente los que distinguen a un buen programador de hardware de uno que "tuvo suerte".

La rúbrica evalúa el resultado: ¿el sistema hace lo que se propuso? ¿El código es legible y organizado? ¿El estudiante puede explicar sus decisiones de diseño?

Se recomienda que el docente use la rúbrica como evaluación sumativa y que los estudiantes usen la lista de cotejo como herramienta formativa de proceso, completándola durante el proyecto, no solo al final.

---

## Evidencias recomendadas para la evaluación

| Nivel de proyecto | Evidencia digital | Evidencia física | Evidencia reflexiva |
|---|---|---|---|
| Bloques sin sensores | Captura de pantalla del programa en MakeCode | Demostración en vivo de la placa | Lista de cotejo completada |
| Bloques con sensores | Captura + video corto del sistema en funcionamiento | Circuito montado | Lista de cotejo + nota de calibración |
| Texto (Arduino / MicroPython) | Archivo de código + captura del monitor serial | Circuito montado | Lista de cotejo + comentarios en el código |
| Proyecto integrador | Repositorio con código, README y fotos | Sistema funcionando | Presentación oral o escrita |

---

## Modalidades de evaluación

**Autoevaluación:** el estudiante completa la lista de cotejo evaluando su propio proceso. Especialmente valiosa en la sección de depuración: ¿realmente usó el monitor serial o adivinó los umbrales?

**Coevaluación:** un equipo prueba el proyecto de otro y responde preguntas específicas: ¿el sistema hace lo que dice que hace? ¿Pudieron entender el código con el README?

**Evaluación docente:** el docente usa la rúbrica mientras el estudiante le explica oralmente su proyecto. La explicación oral revela la comprensión real mejor que el código solo.

---

## Notas docentes

La evaluación de proyectos de programación física tiene un reto particular: es difícil evaluar el proceso porque sucede en tiempo real y no queda registro visible. La lista de cotejo resuelve esto pidiendo al estudiante que registre sus acciones durante el proceso, no solo al final. Enseñar al grupo a completar la lista durante el proyecto (no como tarea posterior) requiere establecer el hábito desde el primer proyecto, aunque sea de forma parcial.
